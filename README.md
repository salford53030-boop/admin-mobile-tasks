# مهام الجوال

واجهة عربية مناسبة للآيفون لإضافة مهام إلى `public.mobile_tasks` في المشروع `ozoulexfbrygiuawwhqn`.

## التشغيل

افتح رابط GitHub Pages عبر HTTPS. أدخل مفتاح `sb_publishable_…` العام من مشروعك ثم سجّل الدخول بالبريد وكلمة المرور للحساب الموجود. لا يوجد تسجيل مستخدمين جدد. اختيار تذكّر المفتاح يحفظ **المفتاح العام فقط** في هذا المتصفح؛ كلمات المرور والجلسات والمهام لا تُحفظ في localStorage. يلزم تسجيل الدخول بعد إعادة فتح الصفحة.

الملفات اللازمة للنشر: `index.html` و`style.css` و`app.js` في جذر فرع `main`. من Settings → Pages اختر Deploy from a branch ثم main و/(root).

## توافق الجدول

تمت مراجعة تعريف الجدول في لوحة Supabase: `id uuid`, `owner_id uuid`, `company_name text`, `branch_name text`, `title text`, `description text`, `priority text`, `due_date date`. الأولويات `low`, `normal`, `high`. تترك الصفحة `created_at` لقيمة الخادم الافتراضية ولا تغيّر `synced_at`.

يعتمد الأمان على RLS في الخادم. يجب أن يكون INSERT محصورًا بـ `authenticated` و`WITH CHECK (auth.uid() = owner_id)`، وأن يكون SELECT مقيدًا بـ `auth.uid() = owner_id`. لا تُعطَ صلاحيات لغير المسجلين. الصفحة تتحقق من الأعمدة والصلاحية باستعلام `limit=0` بعد تسجيل الدخول؛ هذا لا يثبت عزل المستخدمين.

أثناء المراجعة ظهرت في صفحة السياسات شارة **API DISABLED** وتحذير صلاحيات Data API المخصصة، رغم أن محرر الجدول عرض أنه exposed. يحتاج هذا إلى تحقق من إعدادات Data API ومنح SELECT/INSERT لحساب authenticated قبل اعتبار الاتصال الفعلي مكتملًا. لا تعطّل RLS لمعالجة فشل الاتصال.

## الأمان وحدود التحقق

- لا توجد مفاتيح في المستودع، ولا مكتبات أو تحليلات أو خطوط من طرف ثالث. تقبل الصفحة مفاتيح Publishable الحديثة فقط وترفض مفاتيح JWT القديمة والأسرار.
- عنوان المشروع ثابت، وسياسة CSP تقصر الاتصالات عليه وتمنع السكربتات المضمنة والنماذج الخارجية. GitHub Pages لا يدعم ترويسات مخصصة؛ منع تضمين الصفحة في iframe يحتاج استضافة تدعم `frame-ancestors` أو `X-Frame-Options` إذا أصبح مطلبًا.
- لا تعرض أخطاء الخادم الخام ولا كلمات المرور أو الرموز. خروج المستخدم يمحو الجلسة من الذاكرة ويحاول إلغاء جلسة الخادم.
- كل محاولة جديدة لها UUID. عند نتيجة شبكة غير مؤكدة تُحفظ نفس البيانات في الذاكرة لإعادة المحاولة يدويًا؛ تعارض المفتاح الأساسي لا يُعتبر نجاحًا حتى يُتحقق من صف مملوك للمستخدم. لا توجد قائمة إرسال دون إنترنت.
- تحققنا محليًا باختبارات محاكاة من رفض الأسرار، تسجيل الدخول، توافق الطلب، عدم تخزين الجلسة، إعادة المحاولة دون تغيير UUID، رفض المحاولة بحساب مختلف، واستعادة النموذج بعد النجاح. لم يتم إدخال كلمة مرور حقيقية أو إنشاء صف تجريبي في قاعدة الإنتاج.
- ما زال اختبار تسجيل الدخول والإضافة الفعلي واختبار عزل مستخدمين/رفض الطلب غير المسجل مطلوبًا باستخدام المفتاح العام وحسابات اختبار مصرح بها. لا يمكن إثبات RLS بمجرد فحص واجهة العميل.

## المزامنة مع SQLite

هذه الصفحة تحفظ إلى Supabase فقط. الربط مع SQLite المحلي عمل منفصل يحتاج مكوّنًا داخل التطبيق المحلي: مستخدم مصرح له، سحب الصفوف المملوكة له، إدخالًا/تحديثًا بمعرّف Supabase فريد لمنع التكرار، ومعاملة SQLite ناجحة قبل تأشير `synced_at`. يلزم تحديد اتجاه المزامنة والتعارضات والحذف واستعادة الفشل، ومراجعة سياسة UPDATE قبل اعتمادها. لم تُقرأ أو تُرفع أي قاعدة بيانات محلية.
